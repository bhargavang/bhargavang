Project in focus

Saffron Table

Visit live site ↗ Source code

A demo website for a modern Indian restaurant, built to show what a small restaurant's site can do: menu, gallery, location and online table booking on one fast, mobile-first site.

Every booking sends an email to the guest and to the owner, and staff manage the day's bookings from a password-protected admin page. One settings file rebrands it for another restaurant.

How a booking works

  1. Pick a time

    Date, party size and slot

    The booking page shows the next days and only the times that still have room for that many guests.

    • Next.jspages
    • Availability APIfree slots
  2. Save it

    Capacity checked on the server

    The request is validated and saved. With PostgreSQL, a per-slot lock stops two bookings from overfilling the same time.

    • PostgreSQLstorage
    • Advisory lockcapacity
    • JSON filelocal fallback
  3. Confirm

    Emails to guest and owner

    Both get a confirmation. Locally the emails are written to an outbox folder; in production they go out through Resend.

    • Resend APIemail
  4. Run the day

    Admin page for staff

    Staff sign in to see and update bookings. Production passwords are stored as scrypt hashes, never in plain text.

    • scryptpassword hash
Speed

Lighthouse mobile scores of 90–99 for Performance and 100 for Accessibility, Best Practices and SEO on the production build.

Key engineering

01No overbooked tables

Capacity is checked inside a database lock for that slot, so two people booking at the same moment can't push a table past its limit.

02Photos that load on slow connections

The built-in image optimiser timed out fetching large originals. A custom loader lets the photo CDN resize images instead, so pages stay fast.

03Rebrand in one file

Name, menu, hours, address and colours live in one settings file, so the same build can serve another restaurant.

Project in focus

CareDesk

Source code

An appointment booking system for clinics and salons that still juggle notebooks and phone calls. Customers book a free slot online in under a minute, and staff run the day from a secure dashboard.

It runs on a Java and Spring Boot REST API with a React front end. The demo clinic is made up; the code, tests and CI are real.

How a booking works

  1. Choose

    Service and staff member

    Customers pick what they need and who they'd like to see, or "anyone available".

    • React 19booking UI
    • Vitebuild
  2. Pick a time

    Only truly free slots

    The API works out free times from working hours, service length and existing bookings.

    • Spring BootREST API
    • /api/public/slotsfree times
  3. Book

    Locked in the database

    An appointment claims its 15-minute blocks under a unique key, so an overlapping booking fails even if two requests arrive together.

    • PostgreSQLstorage
    • Unique keyno double booking
    • Flywayschema
  4. Remind

    Confirmation and day-before reminder

    Customers get a confirmation right away and a reminder email the day before their visit.

    • Emailconfirm + remind
  5. Run the day

    Staff dashboard

    Staff sign in to see today's list, mark visits done or no-show, and follow bookings per day.

    • JWTstaff sign-in
Tested hard

The test suite fires 12 bookings at the same slot at once and checks only one gets through, then repeats the race with overlapping start times.

The technology stack

LayerTechnologyRole
BackendJava 21, Spring BootREST API, booking rules, email reminders.
DatabasePostgreSQL, H2, FlywayAppointments and staff hours; H2 for quick local runs.
FrontendReact 19, ViteBooking flow and staff dashboard; home page prerendered.
SecurityJWTSigned-in staff dashboard.
DeliveryDocker Compose, GitHub ActionsTests on H2 and PostgreSQL 17, then a full-stack check.

Key engineering

01Double bookings are impossible

The rule lives in the database, not just the app:

  • 12 simultaneous clicks on one slot give one booking
  • overlapping times with different starts are rejected
  • the database still holds with the app-level check switched off

02CI that runs the real thing

Every push runs the tests on H2 and PostgreSQL 17, builds the front end and starts the whole stack with Docker Compose.

03Documented API

Swagger / OpenAPI docs come with the API, so another developer can try every endpoint straight away.

Project in focus

BudgetX

Source code

A personal finance manager: track salary, EMIs and expenses, see what's left to spend each day and what's safe to invest, with AI guidance that's checked against safety rules first.

Built as Spring Boot microservices behind an API gateway, with an installable React web app. 5 of the 8 planned services are built.

How a request flows

  1. Sign in

    Short-lived tokens

    Users get a 15-minute JWT access token and a 7-day refresh token.

    • JWTauth
  2. Gateway

    One front door

    Every call goes through the gateway, which checks the token and limits each user to 20 requests a second.

    • Spring Cloud Gatewayrouting
    • Redisrate limit
  3. Services

    Small services, own data

    Separate Spring Boot services handle areas like expenses, EMIs and guidance, with data in MySQL.

    • Spring Bootservices
    • MySQLstorage
  4. Events

    Services talk through Kafka

    Changes are published as events, so services stay independent.

    • Kafkaevents

The technology stack

LayerTechnologyRole
BackendJava 17, Spring Boot, Spring CloudMicroservices behind an API gateway.
DataMySQL, RedisService data; rate limiting.
MessagingKafkaEvents between services.
FrontendReact (installable web app)Dashboard on desktop and phone.
DeliveryDockerRuns the same on a laptop and a server.

Key engineering

01Rate limiting per user

Redis counts each user's requests at the gateway, capping them at 20 a second before they reach any service.

02Guidance with guardrails

AI suggestions are checked against safety rules before they're shown to the user.
